# 角色识别（character-recognizer）

让 MaiBot 认出聊天图片里的二次元角色，并且**真的认识她**。

插件把图片替换为 `[图片：描述] 图片[角色名]` 形式的文本标签，让后续对话能自然引用"图里这个人"；
同时把角色的设定、所属作品、关系注入模型请求——只有名字的话，模型知道"她叫阿罗娜"，
却答不出"阿罗娜是谁"。

参考实现：[QlzqQlzq/character-knowledge-plugin](https://github.com/QlzqQlzq/character-knowledge-plugin)（借设计，非 fork）。

## 它和参考实现的四个区别

| # | 参考实现 | 本插件 |
|---|---|---|
| 1 | 角色库取**前 40 个**进提示词（`_characters[:40]`），而新角色是追加到末尾的 | 按**相关性检索**挑候选。库超过 40 个角色后，参考实现会让新教的角色永远进不了提示词；本插件不会 |
| 2 | 只注入 `图片[角色名]` | 额外注入设定 / 作品 / 关系，模型真的有背景知识 |
| 3 | 只有 AnimeTrace 一个反查源 | 融合层按多源设计，角色源与"仅作品源"分开计数；只有**多源一致**才自动贴标签 |
| 4 | 角色库损坏时 `raise`，把 `on_load` 打挂 | 降级为空库 + 改名留证，插件照常启动 |

另外补了 4 个 LLM 工具，让模型能主动查角色、查图、反查出处，而不只是被动等 hook 注入。

## 安装

1. 把整个目录放进 MaiBot 的 `plugins/` 下，目录名 `character-recognizer`。
2. 重启 MaiBot（**必须完整重启**：manifest 在插件加载前校验，热重载不生效）。
3. 在 WebUI 的插件管理里启用，并在插件配置里填 `admin_ids`。

首次启动时 Runner 会在数据目录生成 `characters.json`：

```
data/plugins/org.mai-mai.character-recognizer/characters.json
```

**不要**把它放在插件源码目录下的 `data/` —— 那在真机上不是持久化路径。

### 从旧插件迁移角色库

如果已经用参考插件攒了角色库，把它的 `characters.json` 绝对路径填进配置的
`library.import_from`，首次启动时自动导入（仅在本地库不存在时执行）。
直接覆盖 `characters.json` 也可以：本插件会自动识别旧格式、先备份成
`characters.v1.bak-<时间>.json`，再升级为 v2。

## 配置

编辑 `config.toml`（或 WebUI）。分节说明：

| 节 | 关键项 | 说明 |
|---|---|---|
| `plugin` | `enabled`、`max_images_per_message`、`max_characters_per_image` | 识别开关与单消息预算 |
| `vision` | `provider`、`task_name` | `host`（默认）复用 MaiBot 已配置的视觉任务，**不需要再填密钥**；`gemini` / `openai` 才需要 `api_key` 与 `base_url` |
| `library` | `admin_ids`、`max_prompt_characters`、`pinned_reserve` | 管理员列表；进提示词的候选上限；为反查命中的角色预留的候选位数 |
| `library` | `compress_on_finish` | 默认开：结束登记时整理一遍外观卡（合并同类重复说法，保留造型差异与细节；失败保持原样） |
| `library` | `compress_task_name` | 整理用的 Host 模型任务名，默认 `utils`（纯文本活，别占视觉大模型） |
| `retrieval` | `embedding_enabled`、各 `weight_*` | 向量检索开关与打分权重。向量不可用时自动降级为关键词检索 |
| `anime_trace` | `enabled`、`url` | **默认启用**，免费、无需密钥 |
| `saucenao` | `enabled`、`api_key` | 默认关闭。需自行在 saucenao.com 注册免费密钥。**目前尚未接入 adapter**，配置后仅用于 `/识别探测` 评估 |
| `trace_moe` | `enabled` | 默认关闭。只能识别"这是哪部动画第几集"，**不给角色名**，因此永远不计入角色判定 |
| `fusion` | `auto_apply_single_source` | 默认 `false`：单源命中只注入资料、不贴标签。**错贴一个人名比不贴更伤** |
| `fusion` | `auto_apply_local_confirm`、`local_confirm_min_score` | 默认开启：反查源**一个角色名都没报**时，允许「本地库外观卡检索 + 视觉模型确认」这对双证据自动贴标签。见下方"反查源限流时会发生什么" |
| `injection` | `inject_persona`、`inject_work` | 注入哪些字段 |
| `cache` / `circuit` | `ttl_seconds`、`failures` | 缓存有效期与熔断阈值 |

`admin_ids` 支持 `123456789` 与 `qq:123456789` 两种写法（配置侧与运行时侧走同一个归一函数）。

### 反查源限流时会发生什么

AnimeTrace 是免费源，实测会成段返回 `429`（真机日志里 `请求过于频繁，请稍后再试`）。
限流期间**反查恒为空**，所以插件准备了三级应对，从强到弱：

| 层级 | 触发条件 | 行为 |
|---|---|---|
| 1 | 正常反查命中 | 多源一致 → 贴标签；单源命中 → 只注入资料 |
| 2 | 反查源报过角色名但不够可信 | 只注入资料，不贴标签（原设计，不越权） |
| 3 | 反查源**没有给出任何高置信候选**（限流/挂掉/无命中，或只有低置信） | 若「本地库外观卡检索命中」且「视觉模型在候选目录里独立确认了同一个角色」，则贴标签，档位记作 `TL` |

第 3 级存在的理由：没有它，限流窗口里每一张图都是"库里有这个人、却报未识别"——
用户自己攒的角色库恰好在他最需要的时候失效。它敢自动贴，是因为要求的是**两条独立
证据的交集**（比默认不贴的单源命中更严），且两条证据都来自本地数据、不受第三方
可用性影响。

**低置信候选不构成一票否决，但"库内分歧"构成。** 反查源返回"低置信"时它自己都不确定，
拿它去否定本地双证没有道理（真机实测：3 条低置信命中就把兜底整条挡住，表现为
"库里有角色、检索也选中了、却贴不上"）。但如果它指向的是**库内另一个**角色，那就是
分歧而非空白，宁可不贴。解析不到库内角色的名字（多半只是别名没登记）不构成分歧——
跨语言场景里源常给日文名而库里只有中文正名，把它当分歧会让兜底在此类图上永远失效。

### `local_confirm_min_score` 该设多少

它比的是 `0.55 × 向量分 + 0.35 × 关键词分` 这个加权和（`retrieval.py` 的 `_score`）。
按检索层的两条入选线（向量 0.35、关键词 0.12）反推，"两条都刚好过"就是
`0.55×0.35 + 0.35×0.12 ≈ 0.23`，默认值 0.25 就取在这里。

**别往上调太多。** 检索分里的向量分是用 `description` 现算的，而 `description` 是视觉模型
每次看这张图现场生成的——措辞一变，向量就变。真机实测同一张图、同一份外观卡，检索分在
**0.34~0.40** 之间浮动。阈值贴着这个波动带，结果就是"同一张图有时贴得上、有时贴不上"，
而且看起来像随机故障（实测：阈值 0.35 时 0.34 被挡、0.36 通过，同一套卡片）。要收紧就收
`keyword_min_score` / `embed_min_score`（那是"什么算噪音"），别拿这个数当第二个噪音门槛。

阈值落进 `0.30~0.42` 时，`/识别状态` 会直接警告并给出建议值 —— 不用等你自己发现症状。

### 为什么不只依赖模型的格式自觉

真机实测出过这样一份视觉模型的原始输出：`evidence` 把某个角色的 5 条外观卡**逐字**抄了
下来、`conflicts` 也是空数组，却填了 `kind=unknown`、`name=""`——它分明认出来了，只是
没按格式把名字写回去，而**一个字段没填就足以让整条候选作废**。

所以候选校验之后还有一道确定性兜底：把模型给的 `evidence` 与库内各角色的 `appearance_cards`
做文本重合度比对（去标点后的字符 2-gram），对得上 2 条以上就判回该角色。仍然要求
`conflicts` 为空；泛泛的词（"长发""少女"）达不到重合度门槛，不会被拿来乱认人。

控制器在 `fusion.auto_apply_local_confirm`（关掉即回到"限流期一律不贴"）；
`fusion.local_confirm_min_score` 抬高可让第 3 级更难触发（更保守）。
向量检索降级时第 3 级一律不生效——候选池本身不完整时，"没搜到别人"不能当成"就是他"。

## 命令

命令需要管理员权限（配置 `library.admin_ids`），全部同时接受半角 `/` 与全角 `／`。

| 命令 | 说明 |
|---|---|
| `/识别状态` | 查看运行状态；**向量检索降级、以及阈值落在检索分波动带里时都会在这里明确显示** |
| `/识别探测` | 用本会话最近一张真实图片探测各反查源可用性；并展开**最近一次识图的链路诊断**（缓存/反查/检索分/视觉确认/判定档位/兜底为何没触发） |
| `/角色添加 角色名 [作品] [关系]` | 开始**登记**：接下来连续发图，每张（或每批）都会并进外观卡；空闲 5 分钟自动结束 |
| `/结束角色添加`（`/完成角色添加`） | 结束登记，汇总这批图建出的外观卡 |
| `/取消角色添加` | 放弃本次登记（这批图不入库） |
| `/识图修正 角色名` | 给**已有**角色补外观卡：直接吃本会话**刚发的图**（默认最多 4 张，15 分钟内的），引用一条消息也可以 |
| `/角色列表`（`/角色库`） | 查看角色库 |
| `/查看角色 角色名`（`/查看人设`） | 查看角色资料 |
| `/设置人设 角色名 文本` | 写角色设定（注入给模型的核心内容） |
| `/设置作品 角色名 作品` | 设置所属作品 |
| `/设置关系 角色名 关系` | 设置与 bot 的关系（会显示在标签后缀里） |
| `/添加别名 角色名 别名` | 加别名。**别名是跨语言匹配的桥梁**：`/添加别名 初音未来 初音ミク` |
| `/删除别名 角色名 别名` | 删别名 |
| `/删除角色 角色名` | 删除角色 |
| `/重建索引` | 清空向量索引与缓存，下次识图重建 |

LLM 工具（无需管理员）：`recognize_image`、`query_character`、`search_character_library`、`reverse_lookup_image`。

## 怎么给角色攒一份好用的外观卡

登记是**连续收集**的——不用一张图建卡再反复 `/识图修正`：

```
/角色添加 鸣澜 蔚蓝档案 搭档
   ↓ 连续发图（一次一张，或一条消息带多张，都行）
「鸣澜」已累积 2 张图、6 条外观卡（发色发型 2｜眼睛 1｜服装 3，本批 +4）。继续发图…
   ↓
/结束角色添加
已结束登记，共收了 4 张图。
「鸣澜」外观卡 13 条（发色发型 3｜眼睛 2｜服装 5｜配饰 3）
▸ 发色发型
  · 浅蓝色长发，刘海整齐覆盖额头，发尾微卷
  · 渐变蓝短发带齐刘海，头顶带有闪电造型的呆毛
▸ 眼睛
  · 金色瞳孔，眼神明亮清晰
▸ 服装
  · 深蓝色短袖制服上衣，领口有白色荷叶边和蝴蝶结
  · …
▸ 配饰
  · 头顶有黑色圆形耳机状饰品，带有发光蓝环
```

**给已有角色补卡**不必重新登记，直接发图再敲命令即可，不用引用：

```
（连发三张换装图）
/识图修正 鸣澜
从 3 张图里为「鸣澜」补充了 9 条。
「鸣澜」外观卡 15 条（发色发型 3｜眼睛 2｜服装 8｜配饰 2）
▸ …
```

它吃的是这个会话**刚发的图**：默认最多 4 张、且只认 15 分钟内的（更早的图不会被当成
"刚发的"用上，免得你事后想不起来这些卡是从哪来的）。

回执**按类别分组**，并在核心三类有缺口时点名——`⚠ 缺「服装」：再补一张能看到这些特征的图`。
分组不是为了好看：那三类正是插件核对候选时用的判据（见「贴错了角色」），
外显出来你才知道该往哪个方向补图。`/查看角色` 看到的外观也是同一套分组。

**发什么图最有价值**：建卡提示词抽的是**发色发型、眼睛、标志性头饰或饰品、服装主调**，
并明确不许写姿势、表情、画面角度。于是——

| 你发的图 | 实际收益 |
|---|---|
| 同一造型的不同角度 | **接近 0**：抽出的卡片几乎一样，去重后只是几条近似重复 |
| **换装 / 不同形态** | **真正的增益**：服装那一类产生新信息 |

一份好卡应当**三类都齐**：发色发型、眼睛、服装主调。理由不只是卡片更全——插件核对候选时
正是按这三类判的（见「贴错了角色」）。回执会按类别列出并点名缺口，缺哪类补哪类即可。
外观卡上限 15 条、精确去重，超出会丢最早的——**被丢掉多少会写在回执里**（`另有 N 条未入库`），
不然你只会看到"又发了几张，卡却没变多"。

### 它不会越攒越重复

两条机制配合，专门对付"发十张图，攒出十条『浅蓝色长发』的变体"：

| 时机 | 做法 |
|---|---|
| 每次抽卡 | 提示词里带上**库里已有的卡片**，只让模型输出没覆盖到的新特征（没有新特征就输出空数组） |
| `/结束角色添加` | 再花一次调用把同类的重复说法合并掉（`library.compress_on_finish`，默认开） |

合并有**三条写死在提示词里**的硬约束，外加一道不依赖模型自觉的兜底：

1. **一条卡只写一类特征**（发色发型 / 眼睛 / 配饰 / 服装）。原卡片就是按类分的，整理必须
   保持这个结构——少了这条，模型会把「造型」当分组键，把每张图的发色+眼睛+服装压成一条
   大杂烩（真机 09-22 就这样把 12 条变成 3 条：整库只剩一类，缺口提示反过来误报缺两类）；
2. **不同造型不许合并**——「蓝色短发」与「浅蓝色长直发」是两种造型。并成一条就丢了形态
   多样性，而识别时正是靠它判断"今天这张图属于哪个形态"；
3. **细节不许丢**——发饰的形状与颜色、服装配件、配色往往就是区分两个角色的唯一线索，
   「精简」最先抹掉的偏偏是它们。

**兜底**：整理完成后会核对**类别覆盖数**，比整理前少就整批拒收、保持原样。提示词写得再
清楚也可能被模型理解歪，所以这道判据不依赖它守规矩。

换句话说：**冗余只是浪费配额，丢细节直接降低准确率**。所以宁可压得少，也不压掉信息；
整理结果明显不合理（条数没减少、或少于 3 条）时一律不采用，调用失败也保持原样。

**它在后台跑**：整理要几十秒，`/结束角色添加` 不会卡着回执等它 —— 卡片清单立刻返回，
整理完成后另发一条通知（成功写「15 → 9 条」并附新清单，失败也只报一行原因）。
整理期间你要是又补了卡，本次结果会被**丢弃**而不是覆盖（旧快照盖掉新卡片是不可接受的）。

**超时卡在哪一层（这一节值得单独读）**：Host 的 `cap.call` RPC 默认超时是 **30 秒**，而视觉模型
实测要 **54.9 秒**。但 SDK 的 `ctx.llm.generate` 在转发到 `cap.call` 时**没有传 `timeout_ms`**
（`maibot_sdk/capabilities/llm.py`），所以每一次都吃那个 30 秒默认值、在 30s 被切断：

```
RPCError: [E_TIMEOUT] 请求 cap.call 超时 (30000ms)
```

**这不是硬限制，是默认值。** 底层 `ctx.call_capability(..., timeout_ms=...)` 是支持覆盖的，
插件现在直接调它并显式带上超时（`LLM_RPC_TIMEOUT_MS = 180s`）——**所有视觉调用都因此受益**，
不只是整理。插件侧的 `vision.*` 超时仍然更早生效，所以不会真等满 180 秒。

顺带把整理的默认任务换成了 `utils`（纯文本活没必要占视觉大模型，那只是白白多等 20 秒）：

```toml
[library]
compress_task_name = "utils"   # 默认值；填 vlm 可以退回旧行为
```

没采用时回执/通知会写明**具体原因**（超时 / 模型输出不合规 / 条数没减少 / 整理期间卡片被改动 /
写回失败），而不是一句笼统的"未生效"——这几种情况的处理方式完全不同。

## 安全设计

- **SSRF 防护**：入站消息里的图片 URL 是**攻击者可控**的（部分适配器只保留 url、不带 base64），
  所以下载链路逐层设防——只接受 http/https；主机必须**解析到公网**（只拦字面量 IP 会被
  "域名 A 记录指向内网"绕过）；**手动逐跳跟随重定向**并每跳重新校验（urllib 默认自动跟，
  一条 302 就能把请求带到 `169.254.169.254`）；体积与超时都有上限。
  被拦时会记日志说明原因，好区分「安全策略拦下」与「网络失败」。
- **提示词注入中和**：VLM 描述、反查回来的角色名、外观卡文本都是**不可信输入**（图片内容足以
  诱导模型输出任意字符串）。拼进提示词前一律经 `textutil.neutralize` 打断 `<<<` / `【`
  一类定界序列，避免它们伪造"数据块结束"、把后续内容抬成指令。
- **不向外部服务发送任何凭据**：图片下载与反查请求都不带 cookie / token。

## 权限与隐私

- 图片会发给 AnimeTrace（默认启用）用于角色反查；开启 `vision.provider` 为直连通道时，图片也会发给该视觉服务。
- 发给外部服务的图片副本有体积上限，超限时**自动压缩副本**，原图不被改写。
- 角色库只有管理员命令能写入，普通聊天不会自动新增或修改角色。
- **未配置 `library.admin_ids` 时，管理命令一律拒绝**（fail-closed）。首次部署记得先配管理员，
  否则命令会毫无反应——这是有意为之：库里有 `/删除角色` 这类破坏性操作，宁可默认关闭。
  要放开可设 `library.allow_unrestricted_admin = true`（**仅限本地测试**）。
- 所有网络请求都有超时与熔断；连续失败达到阈值后暂停该源并自动恢复试探。

## 故障排查

**日志里反复出现「视觉请求超时」**

这是模型本身比插件愿意等的时间还长，不是插件故障。真机实测有模型单次要 50 秒，
而识别是**实时路径**，超时设得再大也换不回体验。按下面两条之一处理：

1. **换更快的视觉模型**（首选）。
2. 调大 `plugin.image_timeout_seconds`（识别，默认 50s）或 `plugin.card_timeout_seconds`
   （建卡 / 补卡，默认 90s，比识别宽松——那时你已经预期要等）。
   注意识别还受 `plugin.message_timeout_seconds`（单条消息总预算 110s）约束：
   单张超时调得越大，一条消息能识别的图就越少。

插件在**首次**遇到超时时会把这两条建议直接打进日志，不用回来翻文档。

**角色识别不出来**
1. 先 `/识别状态` 看反查源是否都开着、向量检索是否降级、库里有几个角色（`库为空` 时检索没得挑）。
2. 再 `/识别探测`：它会用真实图片报出各源返回的角色名，以及这些名字**能否命中本地库别名**。
   命中率低是跨语言问题的直接证据，用 `/添加别名` 把反查源常用的写法补进角色库即可。
3. **看探测结果里的「源故障」段落**：如果那里写着 `被限流…（HTTP 429）`，意思是"这次没查成"，
   **不代表图里没角色**——这时候反复重发同一张图只会把限流窗口推得更长，等一两分钟就好。
4. 单源命中默认不贴标签（这是刻意的）。要放宽就开 `fusion.auto_apply_single_source`，但误贴率会上升。
5. 反查源被限流期间靠第 3 级通路兜底（见上文）。它要求角色的外观卡已经建过——
   用 `/角色添加` 或 `/识图修正` 建一次，之后同类图就能自动贴上了。

**怎么定位"为什么这张图没认出来"**

`/识别探测` 末尾会展开最近一次识图的诊断，逐段报出岔路口：

```
最近一次识图诊断：
  缓存：未命中
  反查源：无命中
    · anime_trace: 被限流：请求过于频繁，请稍后再试（HTTP 429） → …
  角色库：1 个角色｜本地检索：鸣澜 0.31
  视觉候选校验：确认了候选（鸣澜）
  判定档位：TE｜标签：图片[未识别]
  依据：所有反查源均无命中
  本地库兜底通路：未触发：模型确认了 鸣澜 0.31，但检索分没过阈值 0.25 → 可下调 fusion.local_confirm_min_score
```

堵点各有各的处理方式，别改错地方：

| 诊断里看到 | 真正的问题 | 怎么办 |
|---|---|---|
| `本地检索：没有候选过线` | 外观卡太薄或写法对不上，检索挑不出它 | 补外观卡（`/识图修正`）、加别名 |
| `无可用候选（模型没有给出任何候选）` | 模型觉得图里不是库内的人 | 换更清晰的正面图 |
| `无可用候选（「（无名）」未被认定为库内角色（kind=unknown））` | 模型认出了，但没按格式填名字（证据通常已对上外观卡） | 插件会自动按外观卡比对救回；仍失败说明特征对不上，补卡 |
| `无可用候选（「X」被判有冲突特征：…）` | 模型认为外观与画像矛盾 | 看它报的冲突是否成立；不成立就补卡澄清 |
| `无可用候选（「X」可见证据不足 2 条）` | 图片信息量不够 | 换信息更全的图 |
| `视觉候选校验：调用失败…` | 视觉任务配置/超时问题，**不是没认出** | 查 `vision.task_name` 与 MaiBot 模型配置 |
| `模型确认了 X，但检索分没过阈值 T` | 检索够了但阈值卡着 | 下调 `fusion.local_confirm_min_score` |
| `反查源指向 Y，分歧时不贴` | 反查源与本地库指向不同角色 | 判断谁对；确认是本地库对就补别名让两者合流 |

诊断还会带出**视觉模型的原始输出**——候选被丢弃时，"它到底写了什么"是唯一能定案的证据。

**贴错了角色**

最常见的原因是模型**只凭发色、瞳色认人**——同发色同瞳色的角色到处都是，而服装主调往往
才是唯一能区分他们的那一类。诊断里的「视觉模型原始输出」会直接给你证据：如果它的
`evidence` 里全是发色/瞳色类、一条服装特征都没有，而 `conflicts` 又是空数组，那就是这一类。

对策有两条：
1. 给库里每个角色补上**服装主调**类的外观卡（`/识图修正` 或 `/设置人设`），让"服装是否相符"
   成为可核对的一类特征；
2. 如果外观卡已经很全、模型仍然乱认，就在配置里把 `fusion.auto_apply_local_confirm` 关掉
   ——那条通路会退回"只注入资料不贴标签"，误贴立刻消失，代价是限流期不再自动识别。

**模型还是不知道角色是谁**
说明角色入库了但没填设定。用 `/设置人设 角色名 ...` 补上——`persona` 是注入的核心字段。

**日志一直刷"向量检索不可用"**
MaiBot 没有配置 `embedding` 任务。要么在 MaiBot 模型管理里配上，要么把
`retrieval.embedding_enabled` 设为 `false` 关掉这项检索——降级到关键词检索照样能用。

**日志提示"图片无法压到上传上限"且环境里没有 Pillow**
AnimeTrace 有上传体积硬限制，超过就得压缩，而压缩依赖 Pillow。装上即可：
`pip install Pillow`。若不加装，大图会被跳过（不影响小图识别）。

**改了 manifest 没生效**
`capabilities` 等 manifest 字段在插件加载前校验，热重载不生效。**必须完整重启 MaiBot**。

**角色加了但识别不到**
先确认库里的角色数是否超过了 `library.max_prompt_characters`——本插件按相关性挑选候选，
不会因为库大就丢掉新角色；但如果该角色的外观卡和设定都太空，检索也挑不出它。
用 `/查看角色` 确认 `persona` 与 `appearance_cards` 都有内容。

## 开发

```bash
# 门禁（静态检查 → 冒烟 → pytest）
bash /c/Users/38160/Desktop/tools/maibot-devkit/gate.sh /c/Users/38160/Desktop/character-recognizer
```

- `plugin.py` 之外的模块**不许出现 `self.ctx`**：静态检查只扫描 `plugin.py` 推导能力名，
  其它模块里写 ctx 会"静态检查全绿、真机拒绝授权"。
- `plugin.py` 不写 `from __future__ import annotations`（pydantic 解析配置模型会失败）。
- 装饰器必须**紧贴**其后的 `def`；组件数由 `tests/smoke_test.py` 的清单断言守住。
- 基线：MaiBot Host 1.2.0–1.99.99 + `maibot-plugin-sdk` 2.8.0。
